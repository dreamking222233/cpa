# Plan: 前端管理中心改造

## 用户原始需求

在当前工作区补充拉取 CPA 官方前端项目 `Cli-Proxy-API-Management-Center`，并将此前已经提出并已在后端侧补充的能力落到可操作的前端页面中，确保可以通过前端完成以下需求：

1. 新增代理池管理页面，可以配置多个 SOCKS5 代理，供后端请求上游时随机使用。
2. 在页面中查看请求日志，展示每次请求的北京时间、模型、输入 token、输出 token、缓存 token、价格估算、使用的授权文件，以及本次请求使用了哪个代理。
3. 在认证文件页面支持批量勾选，并批量启用或批量禁用账号。
4. 前端能力需要和当前后端已经新增的管理接口及页面约束保持一致，不破坏现有 `v1/responses`、`v2/responses` 和图片相关限制逻辑。

## 技术方案设计

### 一、仓库组织

1. 当前目录保留为后端主仓库 `CLIProxyAPI`。
2. 官方前端仓库单独克隆到当前工作区的同级目录或子目录中，不覆盖后端仓库现有内容。
3. 前后端分别维护各自的 Git 历史，后续用户可以：
   - 在后端仓库中保留官方 upstream；
   - 在前端仓库中单独保留官方 upstream；
   - 将各自代码推送到用户自己的 GitHub 仓库，再通过 `upstream + origin` 模式同步官方更新。

### 二、前端改造范围

1. 分析前端技术栈、路由结构、页面入口和 API 封装方式。
2. 对接后端现有/新增管理接口，优先复用已有页面布局、表格、表单、弹窗和请求封装。
3. 需要补充的前端能力：
   - 代理池页面：列表、增删改、启停、随机调度说明、基础校验。
   - 请求日志页面：列表展示、刷新、汇总信息、价格来源说明、代理与授权信息展示。
   - 认证文件页面：批量勾选、批量启用、批量禁用、批量操作后的局部刷新。
4. 如果前端项目已有类似页面，则在原页面上扩展；如果没有，则按现有导航结构新增页面入口与路由。

### 三、联调策略

1. 先确认后端管理接口路径、请求参数、返回结构是否稳定。
2. 前端按接口契约完成请求层和页面层实现。
3. 启动后端与前端本地服务进行联调，重点验证：
   - 代理池配置是否可保存与展示；
   - 请求日志字段是否完整；
   - 批量启停是否正确作用于选中认证文件；
   - 页面文案、错误提示和空态是否可用。

### 四、兼容与风险

1. 前端官方仓库结构未知，拉取后可能与当前后端内置页面能力重叠，需要避免重复实现冲突功能。
2. 后端当前仓库存在较多未提交改动，联调时需要只增量修改，不覆盖既有工作。
3. 如果前端项目和后端接口字段命名不一致，需要在请求层做兼容映射，不反向破坏现有后端接口。
4. 若前端依赖安装或构建依赖外网，需要按权限申请执行。
